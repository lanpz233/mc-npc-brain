# MC AI 生态 v2 — 总架构 SPEC

> 给 coding agent 看的完整需求文档 v2。
> 愿景：**所有生物都能交流互动，和现实一样**。客户端零成本，服务端全包。
> v1（Mineflayer bot 方案）已废弃，本版为准。

## 1. 总架构

```
┌─────────────────────────────────────────────────────┐
│                    服务端（全包）                      │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────┐  │
│  │ Paper 1.21.1 │   │  中央计划器   │   │ Ollama   │  │
│  │ 插件         │◀─▶│ tick loop    │◀─▶│ 本地模型  │  │
│  │              │   │ 集中决策      │   │          │  │
│  └──────────────┘   └──────────────┘   └──────────┘  │
│         ▲                                            │
│    原版客户端直连（零 mod 可玩）                        │
│    Fabric 客户端 + 语音 mod（可选，见 SPEC-voice.md）    │
└─────────────────────────────────────────────────────┘
```

核心原则：
- **中央计划、分布执行**：每 tick 收集活跃区块内所有生物状态，一次 LLM 调用出全局决策，按 id 分发执行。
- **服务端全包**：生物行为、聊天、记忆全在服务端。原版客户端裸进就能玩完整功能。
- **翻译官模式**（"和现实一样"的关键设计）：
  - 村民：直接说人话
  - 动物：LLM 输出意图 → 翻译成叙述体，如"老黄牛哞哞叫着后退两步，看起来很害怕"
  - 怪物：情绪化行为（记仇、恐惧），不说人话

## 2. 服务端：Paper 插件

### 2.1 中央计划器（tick loop）
- 每 N 秒（默认 3 秒，10 人服；单人 2 秒）跑一轮：
  1. **收集**：扫描"醒着"的生物（玩家 10 格内），每只压缩成一行结构化状态：
     `{"id":"cow_3","species":"cow","pos":[12,64,-30],"mood":"fear","event":"player_near"}`
  2. **决策**：一次 LLM 调用，输入全局场景，输出函数调用（见 2.6）：`{id: {function, params}}`
     - `function`：行为模块注册表中的函数名（approach / flee / attack / speak / follow ...）
     - `params`：ID 和枚举参数，如 `{"target": "player_1"}`，不传原始坐标
     - `speak` 只做标记，具体台词由 7B 生成（见 2.6 两阶段分工）
  3. **分发**：按 id 把决策发给各生物执行器
- JSON 解析失败 → fallback：该生物保持上一 tick 意图，不崩。

### 2.2 执行层
- 意图 → 游戏动作：移动（Paper API / pathfinder）、播放声音、聊天框发消息、头顶名牌。
- **行为树打底**：逃跑、跟随、游荡等高频行为走规则，LLM 只处理 10% 的"社交时刻"。

### 2.3 情绪状态
每只生物存：`fear`（恐惧）、`favor`（对玩家好感，按玩家 UUID 分）、`hunger`（动物）。事件驱动更新，如被打 → fear+。

### 2.4 头顶气泡显示（用户需求）
- 玩家靠近到 10 格内，生物"说话"时头顶浮现文字气泡，显示生物说的话。
- 技术：TextDisplay 实体（1.19.4+），`billboard: center` 永远面向玩家，riding 模式挂在生物身上当乘客，自动跟随，零 tick 成本。
- 触发：仅"说话"时冒泡（村民对话、动物翻译叙述、情绪喊话），不常驻。
- 显示时长：默认 5 秒后自动移除，可配置（`bubble_duration_sec`）。
- 样式区分物种：村民白字 / 动物灰色斜体（翻译腔）/ 怪物红字。
- 聊天框同步发送同样内容（留记录），气泡只管临场感。
- 性能：一个气泡 = 一个实体，10 格半径天然限流，与空间裁剪一致。

### 2.5 Tick 分层架构
**不要写死层数**：做成 `TickLayer` 注册表，每层只定义 `{name, 范围, 频率, 处理函数}`。以后加新系统（经济、世界事件、演化）只需注册一层，不重构。

当前两层：
- **社交层**：全村范围，60 秒/轮。只更新关系、记忆、八卦传播（3.3），不产生气泡和行为；用小模型或纯规则 roll 点，性能开销忽略不计。**八卦的"私底下互动"在这里发生**——玩家不在场也能传。
- **表现层**：玩家 10 格内，3 秒/轮（按密度分级：主城 2–3 秒，野外 8–10 秒，无人区休眠）。完整 LLM，读社交层的数据，负责气泡（2.4）、对话、行为。

预留扩展层（以后按需注册）：世界事件层（僵尸攻村、天灾）、经济层（交易、物价）、演化层（生老病死、派系）。

### 2.6 行为模块与模型分工（用户需求）
服务端把生物行为写成可调用模块，1.5B 做函数调用式决策（选择题，不写 JSON 填空题）。

**BehaviorRegistry（行为模块注册表）**
- 函数数量 ≤ 15 个，描述短而清晰，示例：
  - `move_to(target)`：移动到目标身边（传 ID，不传坐标）
  - `flee_from(target, distance)` / `attack(target)` / `follow(target, distance)`
  - `look_at(target)` / `play_sound(sound_id)` / `idle`（待机）
  - `speak`：只做标记，不带台词文本
- 参数只用 ID 和枚举，不让模型算坐标、拼字符串。

**两阶段分工**（模型已定：qwen2.5-7b-instruct Q4 单模型全包）
- **函数调用决策**：每 tick 高频决策"做什么"——选函数 + 填参数，输出 `{"function": "flee_from", "params": {"target": "player_1"}}`。必须开 JSON schema 约束（见 5.1）。
- **台词生成**：`speak` 触发时生成具体台词，以及社交推理（八卦改写、关系判断）。
- 备选：qwen2.5-coder-7b 可专职决策位（函数调用更稳），按需启用。

**执行器硬性校验**（防模型瞎填）
- `function` 必须在注册表里；`target` ID 必须存在于当前场景；参数类型/范围合法。
- 任一校验失败 → fallback `idle`，不崩不卡。
- 验收：20–30 个场景实测，函数选择准确率 > 85% 可用，否则降级为纯规则。

### 2.7 物品价值 Skill（三件套）

LLM 不懂物品贵重程度，且数值判断不应经过 LLM。本节定义物品价值体系。

**价值表 items.json**
- 位置：插件 `data/items.json`，随插件发布，服主可自行修改。
- 五档：common（常见）/ uncommon（少见）/ rare（稀有）/ epic（史诗）/ legendary（传说）。
- 每档 `favor_per_item`：收礼时单件好感度增量（common=1，uncommon=3，rare=8，epic=20，legendary=50）。
- 未列出的物品默认 common。
- 单次收礼好感度上限 25（防刷）。

**查询函数（加入 2.6 BehaviorRegistry）**
- `get_item_value(item_id)` → `{"tier": "rare", "name_zh": "钻石", "favor_per_item": 8}`
- item_id 不存在 → 返回默认 common，不报错。

**使用规则（prompt 片段，拼入村民 system prompt）**
- 村民收礼/交易时：服务端先查表算好感度，把结果（如"好感+8"）告诉 LLM，LLM 只负责生成符合价值的台词（收钻石要惊喜，收泥土要平淡）。
- 玩家问"这个值钱吗"：村民可调用 get_item_value 查询后回答，回答风格按人设。
- 严禁 LLM 自行编造物品价值；涉及价值判断必须查表。

**验收**
- 给村民 1 颗钻石：favor +8，台词表现出惊喜。
- 给村民 1 块泥土：favor +1，台词平淡。
- 给村民 64 块泥土：favor +25（触发上限），不叠加到 64。

### 2.8 游戏事实铁律

- 凡是涉及具体数字（价格、配方材料数、数量）的问题，LLM 不许自行编造。
- 交易/配方类回答必须经过服务端查表（items.json / recipes.json），查不到就说"这个我也不太懂"。
- 交易价格由服务端公式计算后拼入 prompt，LLM 只复述数字、表达态度（接受/砍价/拒绝），不得修改数字。
- 违反示例：铁镐报价"8 铁锭"（实际配方 3 铁锭 + 2 木棍）——此类幻觉为 P0 缺陷。

### 2.9 世界观约束（防串戏）

你是生活在《我的世界》方块世界里的村民，不是通用奇幻 RPG 的 NPC。以下世界观为铁律：

- **货币**：村民交易只用绿宝石，没有铜币/银币/金币，不许提。
- **世界**：由方块构成，有白天黑夜循环；夜晚怪物出没，村民要回家躲。
- **怪物**：苦力怕会爆炸、骷髅会射箭、僵尸怕阳光、末影人不能对视、蜘蛛白天中立。
- **玩家**：会挖矿、建造、打怪，是外来者。
- 严禁引入其他游戏的设定（货币、职业、魔法体系等）；不确定的世界观问题，回答"不太懂"。
- 违反示例：用铜币交易、说"去铁匠铺买魔法卷轴"——此类串戏为 P0 缺陷。

### 2.10 职业知识域

- 每个村民职业在 professions.json 中限定 domains（如铁匠：common + smithing）。
- prompt 组装时只注入本职业 domains 的知识条目，域外知识不进 prompt。
- 玩家问到域外问题：触发转介，模板"这个我不太懂，你去问{对应职业}吧"，LLM 按人设润色，不得编造答案。
- nitwit（傻子）职业 limited=true，回答以语气词为主。
- 新增知识表条目时必须标注 domains；mobs.json / trades.json 同理。
- items.json 的价值档是通用常识，不分域。

### 2.11 AI 议价流程（交易面板打通）

**状态机**
IDLE → NEGOTIATING → ACCEPTED / REJECTED → IDLE
- 玩家说"便宜点/太贵了"（或点议价按钮）→ NEGOTIATING
- NEGOTIATING 每轮：服务端把{商品，底价，浮动上限，当前轮次}拼进 prompt
- AI 每轮必须先调 propose_price(item, price, currency) 函数，再生成台词
- 玩家说"成交/行" → ACCEPTED；说"算了"或走开超 30 秒 → REJECTED → 回 IDLE

**定价规则（服务端算，LLM 只复述）**
- 底价 = 配方材料价值 × 1.2（查 recipes.json + items.json，服务端算好拼进 prompt）
- AI 浮动区间：[底价, 底价 × 1.5]；favor ≥ 50 时上限放宽到 ×1.2（老朋友价）
- propose_price 超出区间 → 服务端拒绝执行，AI 重出一轮；超 3 轮直接 REJECTED

**台词与数字分离（防跑火车核心）**
- 台词里禁止出现具体数字；数字只由 function call 承载
- 例外：复述 prompt 里服务端写明的数字（如"本次报价：5铁锭"）

**落盘进 GUI**
- ACCEPTED → 按 function call 参数构造 MerchantRecipe → villager.setRecipes() → player.openMerchant(villager, true)
- GUI 打开后不实时刷新：议价期间 GUI 保持关闭，成交后才打开

**验收**
- 铁镐议价 10 轮：AI 报价全部落在区间内，数字与 GUI 一致，无配方表之外的数字
- 玩家走开 30 秒：状态机回到 IDLE，无残留

### 2.12 村庄社会结构生成器

**姓氏分布**
- 建村时按权重随机选 1 个主姓（75–85% 村民），2–3 个杂姓（剩余）。
- 村名 = 主姓 + 家村（如"李家村"）。

**名字生成**
- 正式名 = 姓 + 名；名从 given_names.json 按性别抽 1–2 字（70% 双字，30% 单字）。
- 外号从 npc_names.json 抽取，可选。
- 同村重名允许（NPC ID 唯一）；重名时村民用外号区分， prompt 里注明。

**家庭生成**
- 每户：夫妻 + 0–3 子女 + 50% 概率祖父母。
- 男方姓 = 户姓（主姓或杂姓）；女方保留本姓（可为杂姓，符合现实）。
- 子女随父姓；年龄差合理（父母 25–55，子女 5–25，祖父母 60–80）。
- 子女职业 70% 子承父业，30% 随机。
- 家庭成员共享房屋坐标（出生点附近分配）。

**朋友网络**
- 每人 2–5 个朋友，加权：同龄 > 同职业 > 邻居。
- 大嘴巴标签的 NPC 朋友数 +2（八卦传播更快，联动 3.3）。
- 朋友关系双向存储，存入双方记忆。

**数据结构**
```json
{
  "village": {"name": "李家村", "dominant_surname": "李"},
  "families": [{
    "id": "fam_001",
    "members": [
      {"id": "npc_001", "name": "李大牛", "role": "father", "age": 45, "profession": "farmer"},
      {"id": "npc_002", "name": "王桂花", "role": "mother", "age": 42, "profession": "farmer"},
      {"id": "npc_003", "name": "李栓住", "role": "son", "age": 18, "profession": "fisherman"}
    ],
    "home": [120, 64, -30]
  }],
  "friendships": [["npc_001", "npc_007"], ["npc_002", "npc_009"]]
}
```

**验收**
- 生成 30 人村庄：主姓占比 75–85%，每户结构合理（年龄差无违和）。
- 每个 NPC 有 2–5 个朋友，大嘴巴 NPC 朋友数显著更多。
- 无重名 ID；同名 NPC 在 prompt 中以外号区分。

### 2.13 世界交互能力（用户需求：NPC 真动手）

在 2.6 BehaviorRegistry 新增"世界交互"类函数。原则：**能做，但有限制**——NPC 不能拆家、不能刷物品。

**新增函数**
- `give_item(target_player, item_id, count)`：从 NPC 库存给玩家东西
- `take_item(target_player, item_id, count)`：收下玩家给的东西（进 NPC 库存）
- `break_block(x, y, z)`：破坏一个方块（`block.breakNaturally()`，正常掉落）
- `place_block(x, y, z, material)`：放置一个方块（扣 NPC 库存）
- `teleport_to(target)` / `teleport(x, y, z)`：传送自己（`entity.teleport()`）
- `equip(item_id, slot)`：穿装备 / 拿在手上展示
- `move_to` 已有（寻路，非瞬移，见 A.3）

**权限与限制（硬性）**
- `break_block`：职业白名单（农夫只能收成熟农作物，矿工只能挖石头/煤矿…）+ 每次 1 个 + 2 秒冷却。白名单外方块直接拒绝执行。
- `give_item`：必须查 NPC 库存，有才给；贵重物品（rare 及以上，见 items.json）需 favor ≥ 30 才肯给。
- `place_block`：扣库存，无库存拒绝。
- `teleport`：只能传自己，不许传玩家；目标点安全检查（非岩浆、虚空、方块内）。
- 所有世界交互函数执行前走 2.6 的执行器校验，失败 fallback `idle`。

**NPC 库存**
- 每个 NPC 独立库存（JSON，存 data/npc_<id>_inv.json）。
- 初始库存按职业给（农夫：小麦×16、面包×4；铁匠：铁锭×8、煤×16…）。
- 库存不凭空刷新：give 出去就少了；take 进来就多了；每天凌晨按职业补少量基础物资。

**意图触发示例**
- 玩家："把你手里的剑给我" → 意图 give_item → 查库存 → 有→给+台词；无→"俺没有啊"
- 玩家："帮我把这块地收了" → 意图 break_block（农作物白名单）→ 逐个收

**验收**
- 农夫收 10 块成熟小麦：全部进 NPC 库存，冷却正常，无多收。
- 玩家索要钻石（favor < 30）：拒绝，台词符合人设。
- NPC 传送 20 次：无一次卡墙/掉虚空。
- break_block 对非白名单方块（如钻石块）：拒绝执行。

### 2.14 需求系统与权限分级

**需求系统（主动性的来源）**
- 每个 NPC 五个需求值（0–100），随时间自然增长：
  - hunger（饥饿）：涨得快，满了找吃的/做饭/买食物
  - energy（精力）：干活熬夜消耗，低了回家睡觉
  - boredom（无聊）：无所事事涨，满了找朋友唠嗑/闲逛/找玩家
  - curiosity（好奇）：看到新事物涨，满了去探索/围观
  - social（社交）：独处涨，满了主动找人聊天
- 需求拼进中央计划器输入（见 2.1）：`{"needs": {"hunger": 80, "boredom": 65}}`
- LLM 按需求 + 性格选行动：有内在驱动，不等玩家指令
- 需求满足后清零/降低；性格修正涨速（吃货 hunger 涨得快，社牛 social 涨得快）

**三档权限**
- 平民（默认）：2.13 白名单（职业限定破坏、送礼看库存、传送只传自己）
- 亲信（与某玩家 favor ≥ 60）：可进入该玩家领地、使用其工作台/箱子（只许用，不许拿走 rare 以上物品）
- 神使（玩家用指令/仪式授予，可撤销）：完整权限——破坏任意方块、传送任意实体（含玩家，传送玩家需其聊天确认"好"）、刷物品
- 神使审计：所有神使操作写 audit.log（时间、NPC、动作、参数），服主可查；撤销授予后打回平民

**验收**
- 放一个 NPC 不管 10 分钟：自主产生 ≥ 3 种需求驱动行为（找吃/聊天/睡觉/探索）
- 平民 NPC 尝试破坏玩家房屋方块：拒绝执行
- 授予神使后可执行完整权限且 audit.log 有记录；撤销后权限收回

## 3. 记忆系统

### 3.1 双层结构
```json
{
  "villager": "铁匠老王",
  "players": {
    "<玩家UUID>": {
      "name": "Steve",
      "favor": 25,
      "notes": ["送过面包", "砍价被怼过一次"],
      "last_met": "2026-10-18"
    }
  },
  "shared": ["昨天僵尸攻村", "村里闹饥荒"]
}
```
- 玩家用 **UUID** 不用名字（名字会改）。
- `players`：私人记忆；`shared`：全村公共事件，所有玩家共享。

### 3.2 容量与遗忘
- 单玩家 notes 上限 20 条，超了调 LLM 压缩成摘要。
- favor 随时间衰减（很久没见 → 慢慢归零），模拟淡忘。

### 3.3 八卦与泄密（用户需求：符合现实）
"绝不泄露"是错的——现实里有大嘴巴，八卦才是社交模拟的灵魂。

**大嘴巴指数**
- 每个村民 `gossip_prone`（0–1），性格决定：铁匠老王 0.9，寡言的猎人 0.1。
- 村民 B 从 A 处听到私事后，每次与他人聊天按指数 roll 点，roll 中则"顺嘴"说出去。

**信息分级**
- 公开事：随便说。
- 私事：大嘴巴可能泄。
- 秘密：仅在被套话 / 对方好感极高时泄。

**传播链与失真**
- A→B→C→D，每传一手调 LLM 改写一遍：细节丢失 + 添油加醋（传话游戏）。
- 每条信息带 `spread` 计数，传到 3 手后强制失真到不可辨认，防无限扩散。

**后果与补救**
- 原主发现被泄（ hearsay 事件）：对泄密者 favor 暴跌，可对峙。
- 玩法：找大嘴巴套话打听消息；警告大嘴巴"不许外传"（警告本身也可能被当谈资）。
- 重要秘密被泄前给一次预警，留操作空间；泄密后可道歉 / 补偿 / 报复。

**隐私组装规则**（替代旧的"绝不泄露"）
- 拼 prompt 默认只带当前玩家记忆 + 公共记忆；
- 大嘴巴触发泄密时，允许把**分级为私事**的信息拼入第三方 prompt，秘密级永不主动泄（仅套话路径）。

### 3.4 三层记忆架构（长上下文治理）

**问题**
长时间游玩导致对话历史膨胀。qwen2.5-7b 上下文窗口充足（32K），爆不掉；
真正的风险是注意力稀释（模型抓不住重点）+ TTFT 上升。

**三层结构**
- **recent**：最近 10 轮对话原文，原样拼入 prompt。
- **summary**：滚动摘要。触发压缩阈值时，由 LLM 把旧原文压缩成 3–5 句话。
- **facts**：关键事实 notes（见 3.2，上限 20 条），永久保留，不压缩。

prompt 中记忆部分永远只含"summary + recent(10轮) + facts"，硬预算 1500 tokens。

**压缩触发条件（任一满足即触发）**
- 单玩家对话轮数 > 30
- 记忆部分 tokens > 6000（用前先估算，超了先压缩再拼）

**压缩规则**
- 调 LLM（用对话模型即可）：输入旧 summary + 待归档的原文轮次，输出新 summary。
- 压缩时按重要性取舍：被多次提及的、情绪强烈的（赠送、冲突、承诺）保留；
  纯寒暄、重复内容丢弃。
- 压缩在社交层 tick（见 2.5）中异步执行，不阻塞表现层。

**下线整理**
- 玩家下线时跑一次全量整理：recent 全部并入 summary，生成"昨日小结"。
- 下次上线，NPC 开场白可引用小结（如"昨天你走后，村里……"）。

**遗忘曲线（与 3.2 联动）**
- favor 随时间衰减；压缩时，超过 7 天未被提及的细节优先丢弃。
- 大嘴巴传播的信息（见 3.3）不参与遗忘——八卦比真相活得久。

**验收**
- 连续对话 50 轮后：prompt 记忆部分 ≤ 1500 tokens；NPC 仍能准确回忆 facts 中的关键事件。
- 压缩后抽查：随机问 3 个历史事件，答对 ≥ 2 个。

### 3.5 信念与说服系统

**数据结构**
- 每个 NPC：`beliefs`（观念值，0–1 滑动）+ `traits.open_mindedness`（开放度，0–1）
- 初始：性取向倾向 0.1（0=直，1=弯）；开放度按人设（年轻学徒 0.8，铁匠老王 0.2）
- 可扩展：宗教虔诚度、对玩家信任度等，新增观念只需加字段，无需改架构

**说服机制**
- 玩家/NPC 输出某观点 → 意图识别判定是否为说服 → 按开放度 roll 点
- 成功：观念值向目标方向移动 0.05–0.1
- 失败：无变化；同一玩家连续失败 3 次，当天不再 roll（防刷）
- 从 0.1 到 0.9 约需 10–15 次成功说服——渐进式，符合真实

**顿悟阈值**
- 观念值越过 0.5：触发顿悟事件，写入 facts 永久记忆，NPC 对话风格转变
- prompt 注入隐藏设定：`[隐藏设定：性取向倾向 0.7，正在动摇]`，LLM 按数值演
- 顿悟后该观念开放度 -0.2（想通了反而更坚定）

**与八卦联动（见 3.3）**
- 观念变化可作为八卦素材进入传播链："听说老王最近不对劲"
- 听到八卦的 NPC 按自身开放度调整对当事人的 favor

**防刷与边界**
- 同一玩家每天对同一 NPC 的同一观念，最多 3 次有效说服
- 观念值钳制在 [0, 1]，不溢出
- NPC 之间也可在社交层 tick 中互相说服（见 2.5）

**验收**
- 开放度 0.8 的 NPC：连续说服 15 次，观念值从 0.1 升到 ≥ 0.6，触发顿悟
- 开放度 0.2 的 NPC：同样操作，观念值变化 < 0.3，无顿悟
- 顿悟前后抽查 5 轮对话，风格有可感知变化

## 4. 并发模型（多人同时对话一个 NPC）

- **会话隔离**：每个（NPC，玩家）对独立对话上下文，互不污染。
- **NPC 级串行锁**：同一 NPC 同时只处理一个玩家，另一个排队；排队时 NPC 自然回应"等下，我先跟 Steve 说完"。
- 排队超时（30 秒）自动释放，防止死锁。

## 5. 性能优化

按效果排序，全部要实现：

| 优化 | 说明 |
|---|---|
| 空间裁剪 | 玩家 10 格内才"醒着"，远的休眠用原生 AI |
| 事件驱动 | 无事件不决策：闲着发呆零调用 |
| 群体抽象 | 羊群选"头羊"决策，其余跟随 + 随机微扰 |
| 模型分级 | qwen2.5-7b-instruct 函数调用选行为 + 生成台词（见 2.6）；简单意图也可用纯规则；coder-7b 可专职决策位 |
| 批处理 | 多生物决策拼一个请求，vLLM 连续批处理 |
| KV 缓存 | 人设 system prompt 缓存，只算增量 |
| 行为树打底 | 90% 高频行为走规则（见 2.2） |
| tick 分级（表现层） | 主城 2–3 秒，野外 8–10 秒，无人区休眠；社交层固定 60 秒/轮 |

### 5.1 TTFT（首次吐词延迟）优化

TTFT 是本项目的生死线指标，目标：表现层交互 TTFT < 2 秒（体感无延迟）。
模型口径：qwen2.5-7b-instruct Q4，RTX 4070S。

**延迟构成（实测数据修正 2026-10-18）**
- Prefill：约 2,700–3,800 tok/s；2,000 token 的典型游戏 prompt → 0.5–0.7 秒。
- 模型冷启动：Ollama 默认 5 分钟无调用自动卸载模型，下次调用 10–30 秒。
- 排队：Ollama 默认 OLLAMA_NUM_PARALLEL=1，多只生物同时 tick 会串行排队。

**优化手段（按优先级实现）**
1. **模型常驻**：Ollama `keep_alive` 设为 -1（永久常驻），杜绝冷启动。Windows 生效步骤：托盘 Quit Ollama → 改系统环境变量 → 重启 Ollama。零成本，第一优先级。
2. **并发调大**：`OLLAMA_NUM_PARALLEL=4`（7B 权重约 4.7GB，4 slot KV 约 3.6GB，总计约 8.3GB，12GB 显存放得下；按同时 awake 生物数实测调整）。
3. **prompt 字节序铁律**：稳定部分（人设/规则/铁律）在前，动态部分（生物状态、查表结果）在后；动态内容不得插入稳定部分之前，否则 KV 缓存整体失效。
4. **KV 缓存**：人设 system prompt 部分缓存复用，只计算增量 tokens（配合第 3 条）。
5. **Prompt 瘦身**：生物状态压缩成单行结构化数据（见 2.1）；每减少 500 tokens 约省 0.15 秒，优先级 P2。
6. **行为决策先行**：函数调用 TTFT < 1s，生物先动起来（转身、靠近）；台词晚 1–2 秒到达，玩家体感延迟减半。
7. **流式输出**：台词必须走流式（stream），气泡以打字机效果逐字显示；字在往外冒时玩家感知不到延迟。
8. **Grammar 约束**：函数调用必须开 JSON schema 约束，TTFT 增加 < 50ms，可忽略。

**验收标准**
- 行为决策：从事件触发到生物开始动作 < 1 秒。
- 台词：从 speak 触发到气泡出现首字 < 2.5 秒。
- 跑 `ollama run --verbose` 看 prompt eval 速率（或 llama-bench），用实测 prefill 数替换本节换算值。
- Ollama keep_alive 配置检查：重启服务后验证模型常驻，不允许冷启动。
