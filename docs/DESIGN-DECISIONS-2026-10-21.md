# mc-npc-brain 设计决策记录（2026-10-21 讨论）

> 本文件记录项目所有者 Fong 与设计讨论中确认的规矩与方向，作为后续源码审计（阶段 0）
> 和各阶段改造的依据。每条结论标注状态：**已定**（Fong 已确认）、**暂定**（讨论中提出的默认值，Fong 未明确确认，可改）、
> **待定**（尚未讨论或尚未拍板）。正文用大白话写，Fong 本人可直接阅读；每节末尾的「实现备注」
> 是给后续写代码的 agent 看的现状与落点。
>
> 审计基线：仓库 HEAD `e4f89aa`（v0.1.2，Paper 1.21.1 / Java 21）。

---

## 0. 总原则（已定）

**插件裁决，AI 表达。** 凡是涉及物品、方块、价格、关系数值变化的事，先由插件按确定规则算出
结果（允许 / 拒绝 / 需要确认，以及数量、价值上限、价格下限），AI 模型只能在这个结果范围内
选择动作和台词，不能改变结果。Paper 服务端是世界真实状态的唯一权威（与原任务书一致）。

背景：Fong 判断当前插件端权限/规则太少，大多数决策靠模型发挥，很不稳定。审计证据支持该判断
（见第 1 节）。

## 1. 现状审计要点（讨论依据，非决策）

以下均为对 HEAD `e4f89aa` 的实际代码核查结论，正式审计文档 `docs/architecture-audit.md` 仍需按任务书阶段 0 补齐：

1. **统一工具系统已存在但只覆盖一部分动作**：`tool/` 包已有 `NpcTool / ToolRegistry /
ToolDispatcher / ToolContext / ToolRequest / ToolResult / ToolPolicyService /
GameStateProvider / NpcTaskManager`，`McaiPlugin` 注册 8 个工具（5 个只读查询、
`npc.task.get`、`npc.task.cancel`、`npc.move_to`），且有单元测试。
2. **双轨并存**：对话模型的旧工具集（`ai/BehaviorRegistry`：`say / move_to / give_item /
accept_swap / break_block / place_block / teleport_to / teleport / equip / offer_trade /
learn / follow_player / flee / find_shelter` 等）经 `planner/CentralPlanner.executeDecision`
→ `security/WorldInteractionService` 执行，不走统一分发，校验口径不一。
3. **插件端权限很窄**：`security/PermissionManager` 只有三档等级（平民/亲信/神使）和
`canBreak / canPlace / canTeleportOthers / isRarePlus` 四类判定；`tool/ToolPolicyService`
自述「规则保持最小」，且 8 个统一工具全部为 `Risk.LOW`，高风险闸门实际永不触发；
无速率限制、无配额、无价值上限。
4. **大量规则只写在提示词里**：`ai/PromptBuilder` 约 1286 行，含大量 "IRON LAW / NEVER…"
式约束（不许编造事实、对话中不许答应移动、亲信不许拿 rare 物品等），靠 9B 模型自觉遵守。
5. **任务不持久化**：`tool/NpcTaskManager / NpcTask` 无任何落盘代码，服务器重启任务全丢。
无村庄级库存、资源预留和经济账本。`planner/SocialLayer` 存在面包保底投放（少于 8 补到 8），
与未来生产链的库存守恒验收冲突，需在经济系统前处理。
6. **数据双份手工同步**：`data/` 为可信源，`src/main/resources/` 为打进 jar 的副本，
靠人工同步；`data/items.json`、`data/npc_names.json` 在 resources 中无副本。

## 2. 权限与规则收回插件（Policy 层）（已定方向）

- 不只是给现有权限类加方法，而是把「谁能做、什么条件下能做、做到什么程度」集中为插件的
确定性裁决层；旧工具路的动作（第 1 节第 2 条）要逐步迁入统一裁决，不再各写各的校验。
- 阶段 0 审计需额外交付一张**权限矩阵**：每个动作标注——现在由谁决定、插件现在校验什么、
哪些约束只存在于提示词里。

实现备注：优先评估把 `WorldInteractionService` 的动作迁入 `ToolDispatcher` + 扩展
`ToolPolicyService`（加入价值上限、配额、冷却、距离与状态前置条件），或至少让两条路共用同一
Policy 实例。禁止新增第三套校验。

## 3. 背包与钱包（已定）

现状问题（Fong 提出，代码已证实）：`mob/VillagerState.seedProfessionInventory` 用同一模板
生成背包——人人固定 8 个面包（农夫 16），随机 2-3 种职业物品（1-8 个）、1-3 种随机零碎
（1-5 个）；背包只是一个「物品名 → 数量」的表，不分用途，**没有钱包**，绿宝石只出现在
买卖价格里。

新设计：背包分四个「兜」，第一次见面生成一次并持久化，之后只能因真实事件
（挣钱、花钱、吃、送、收、交易）变化，不许每日重随：

| 兜 | 内容 | 要点 |
| --- | --- | --- |
| 吃食兜 | 按职业/地域不同的食物（农夫薯类、屠夫肉类、渔夫鱼类等），约 3-8 个 | 村民自己吃，也可用于送礼与救急 |
| 干活兜 | 职业货物（铁匠的铁、农夫的庄稼等），量可较大 | 谋生本钱，走买卖，不走赠送 |
| 钱包（新增） | 绿宝石为主：普通村民约 3-10 个，从商/铁匠约 12-30 个；可带少量铁粒/金粒/矿物作零钱 | 卖货收入进钱包，收购与救急从钱包出；钱包空了收购停止 |
| 私人物兜 | 1-2 件体现性格的小物（花、书、钟、种子等） | 拉开个体差异；平时送礼的主要来源 |

## 4. 送东西（已定框架，数值为暂定）

分三种情形，全部由插件先裁决，AI 只负责语气：

1. **平时送礼**：主要送私人物兜与吃食里的小东西；关系越好，上限越宽。贵重物品**不是绝对
禁止**：关系很好且村民自身宽裕时，可送少量绿宝石或一件像样的东西，但有价值上限和次数
限制，不能天天送。
2. **玩家开口要**：插件按关系、物品价值、村民余量裁决给不给、给几个。
3. **救急**：见第 5 节，优先级最高，走独立规则。

（暂定数值）单次最多 3 个普通物品；村民自留口粮至少 4 个。

## 5. 救急与村庄信任（已定）

1. **触发（插件看真实数字，三条全满足）**：玩家血量见底、饥饿度很低、玩家背包里确实
没有任何食物。
2. **救法**：附近村民优先给食物（约 2-3 个，先续命）；村民没食物但有钱时给约 2-5 个
绿宝石让玩家去买。关系越好，给得越多。
3. **单人限制（已定）**：同一个村民，一天（游戏内一天）最多救同一个玩家一次。
4. **全村总上限：不设（已定）**。原讨论曾提议「全村一天最多 3 次」，被下面的声誉机制
取代，不再采用硬上限。
5. **声誉机制（Fong 提出，已定）**：被救是真实事件，会通过村民间的传话流传开
（现有 `planner/SocialLayer` 已有八卦传播：见闻在 NPC 间缓慢扩散且非人人采信，可复用）。
- 第一次被救不扣信任，只有同情；
- 短期内反复被同一个村子救，全村对该玩家的**村庄级信任**（区别于单个村民的好感）
逐步下降；
- 信任下降后帮助自动缩水：先减钱、再只给吃的、语气变冷；
- **底线：信任太低时，全村完全停救，连一口吃的也不给；**
- 名声可恢复：长期不再出事自然回升；在村里正常交易、帮忙、送礼等好事同样会传开，
可把信任挣回来。

实现备注：需要新增「村庄」归属与村庄级声誉的持久化记录；救急事件须作为可验证事件入账
（谁、何时、给了什么），不得由 AI 虚构或改写数值。

## 6. 定价（已定）

现状问题（代码已证实）：

- 价目表（`ai/TradeRegistry`）东拼西凑、无统一标准：卖价普遍远高于原版
（如钻石胸甲 50 绿宝石无附魔，原版大师盔甲匠附魔钻石甲约 13-35；金胡萝卜 8 绿宝石/个，
原版约 1 绿宝石/个；普通弓 20 绿宝石，原版约 2），收购价个别又过于大方
（图书管理员收纸 1 张给 2 绿宝石，原版 24 张纸换 1 绿宝石）。
- 玩家在聊天里说出「数字 + 绿宝石 + 商品名」，插件即把价格改成玩家报的数字并上锁
（`CentralPlanner.interceptBargain`），无底线、无谈判。
- AI 可任意上架、任意定价（仅校验 ≥1）、任意降价；`offer_trade` 的 price=0 免费送路径
**不扣村民库存**，等于凭空造物（单次上限 16 个）。

新规矩：

1. **锚定原版**：原版村民有对应交易的，直接以原版价格为基准价。
2. **扩充商品保留**：原版不卖的东西（如附魔台、图腾）继续卖，按原版价值体系换算：
- 能合成的按材料价值估（附魔台约十几到二十绿宝石量级，不再是 128）；
- 只能靠探险/打怪获得的稀有物按稀有档定价（图腾约二三十绿宝石量级），且
**村民真有库存才卖、卖完不自动补货**。
3. **收购价同样锚定原版**，堵住「1 张纸换 2 绿宝石」式印钱口。
4. **取消凭空免费送**：一切赠送统一走第 4 节规则，必须从真实背包/钱包扣除。
5. **上架必须有货**：只能卖背包里真实拥有的东西，价格由插件按价值表定，AI 最多在
小范围内浮动提案，最终价以插件为准。
6. 价格浮动因素（关系、村庄信任、存货多少）只在基准价上下小范围作用，由插件计算。

## 7. 砍价（已定稿，2026-10-21 随交易 UI 落地）

- 砍价只发生在商店界面里：玩家**自己选择砍多少钱**（整数绿宝石），插件守底线。
- **不用百分比折扣**（Fong 定）：交易货币是整数，打折会出现小数；让价一律整数块数。
- 底线由插件按好感算（`security/BargainPolicy`）：生人最多让 1 块、熟人 1+标价/5、
  交情 2+标价/4、亲信 3+标价/3；成交价永不低于 1 块。原暂定 7/6/5 折方案作废。
- 玩家选的砍幅在让价额度内 → 按玩家要的价成交；超了 → 村民**还价到底线价**，
  玩家在界面点「接受」才落定，不接受维持原价。
- 谈成的价记在交易会话（ShopSession）里，同一商品一次会话只砍一次；关窗聊天再回来不丢。
- 模型无权改价：`offer_trade` 的 discount 动作已退役，聊天里报数字不再改价（只识别并
  注入事实说明，防模型在台词里许诺插件不会兑现的价）。
- 结算时以会话成交价重算扣款，界面显示不算数（`shop/ShopSettlement`）。

## 8. 交易系统与 UI（已定路线二）

- 交易从对话/原版交易窗口中**独立出来**，做成单独的交易系统（Fong 提出）：操作走界面
按钮，不靠聊天猜，降低自由度与出错空间。
- **路线二**：服务器留在 Paper 1.21.1，不升级版本；用服务器资源包给商店界面换皮
（柜台背景、商品摆位、价签、按钮牌子）。玩家进服时点一次同意下载资源包；拒绝资源包的
玩家看到朴素版界面，功能不受影响。
- 界面要素：
- 商品区：名称、库存、当前价（插件填写，所见即所付）；
- 按钮：插件当场验钱、验货、扣款交货；
- 按钮：点一次 = 一轮，插件按第 7 节算出新价并立刻刷新界面，村民台词显示在
界面上方对话栏；到底线后按钮变灰标明「已是最低价」；
- ：用带输入框的小弹窗（铁砧改名框，资源包一并换皮）让玩家填数字，
插件拿去与底线比较后接受或还价；
- 分页：收购款从村民**钱包**出（见第 3 节），钱包空了停收；
- 预设台词按钮（如打招呼、提人情）：点 = 说一句话，村民在对话栏回应；
- 关界面再回来，砍价进度与已谈价格由插件保存，不丢失。
- **已知限制（接受）**：路线二（箱子窗口 + 资源包）**没有界面内打字聊天框**——窗口打开时
客户端不允许打字聊天，资源包只能换皮、改不了窗口能力。替代办法即上面四条：对话栏看
村民说话、预设台词按钮、关窗自由聊天再回来（进度不丢）、铁砧框输入。
- 路线一（升级到 Paper 1.21.7+ 用官方 Dialog 表单：真按钮、真输入框）**暂缓**，不在本期
范围内；将来若升级版本，可与路线二结合（摆货用资源包商店、砍价确认用表单）。

## 9. 对话开始与结束（已定）

- **右键结束对话保留（已定）**：右键开始、再右键同一村民结束，这个交互不改；
误触问题不靠改交互解决，靠下面这条让重开不突兀。
- **废除固定开场指令（已定）**：现状 `listener/PlayerInteractListener` 每次开始对话都给 AI
发同一句合成指令（大意「玩家刚过来想聊天，热情打招呼」），且它以玩家发言的形式进入
聊天记录，每右键一次堆一条。村民记忆其实未被清空（`startConversation` 明确保留
recent/summary/facts），突兀感纯粹来自这条指令。
- 新做法：开场说明由插件按事实**动态拼装**，至少包含：
- 是否见过（第一次才自我介绍）；
- 距上次对话结束过了多久（需新增记录：上次对话结束时间）：几分钟内 = 接着聊，
明确禁止重新打招呼，可接「刚才说到……」；当天内 = 熟络招呼；隔日以上 = 好久不见；
- 上次聊到什么 / 有没有未办完的事（砍价中断、说好去凑钱等），开场先接这件事；
- 当下状态：玩家残血/饥饿（衔接救急）、村民忙碌/受惊、天气与时段等。
- 开场说明是「导演提示」而非玩家发言：不写入聊天记录，不参与玩家句式解析
（可复用现有 systemNote 机制的思路）。

## 10. 模型层遗留决策（待定）

以下来自原任务书与审计发现，本次讨论**尚未拍板**，不要当作已定方案执行：

1. **Qwen 正文提取工具调用的处置**：任务书要求只用 Ollama 原生 `tool_calls`、不降级为
正文提取；但现状 `ai/LLMClient.parseResponse` 在原生调用为空时会从正文提取，
且近期提交还在加强这条路（台词抢救）。审计方建议的折中——正文提取只允许恢复
`say` 类无副作用内容，涉及世界变更的调用一律拒绝执行只记日志——**待 Fong 确认**。
2. **MiniCPM 自由 JSON 模式去留**：现状 `ai/BehaviorDecisionParser` 是容错修复式解析
（与任务书「严格协议」相悖）；候选序号模式（`BehaviorModelClient.decideChoice`：
服务端预生成 2-4 个合法候选、模型只回序号、越界重试一次再回退）更符合任务书精神，
且默认未启用（`llm.behavior.autonomy-enabled: false`）。是否正式废弃自由模式、
只保留候选模式，**待 Fong 确认**。

## 11. 建议实施顺序（供排期讨论，非决策）

1. 阶段 0 只读审计补全（含第 2 节的权限矩阵与双轨调用图），并在有 JDK 21 的环境补跑
`./gradlew test` 留真实结果（讨论时本机无 JDK，测试未运行）。
2. 第 10 节两个待定项拍板。
3. 小而感知强的先行项：第 9 节对话开场改造（独立、改动面小、立刻改善体验）。
4. Policy 收敛（第 2 节）→ 背包与钱包（第 3 节）→ 送东西与救急/信任（第 4、5 节）。
5. 定价表按原版重做（第 6 节）→ 砍价机制（第 7 节）→ 交易系统与资源包 UI（第 8 节）。
6. 后续再按原任务书推进规则行为核心、Qwen 高层规划、多 NPC 协作与村庄经济、
社会关系与长期记忆、MiniCPM 评估。
